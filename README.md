# Viper Racing Modding

A toolkit and app suite for modding *Viper Racing* (1998): parse and rebuild its
file formats, browse and 3D-preview your cars and tracks, edit their textures,
swap tracks into the game's slots, set up the AI field, add modern resolutions,
and check your install for the fixes it needs to run well on a modern PC.

Everything is built on **`vrmod`**, a self-contained Python toolkit (pure standard
library apart from `capstone`, and even that only for one optional patch). The same
`vrmod` powers three front ends:

| Front end | What it is | Where |
|---|---|---|
| **`vrmod` CLI + toolkit** | Parsers/builders for every format, plus a local web UI | [`vrmod/`](vrmod/) |
| **Viper Racing Mod Manager** | A native desktop app (pywebview) around the web UI | [`desktop/`](desktop/) |
| **Viper Racing Library** | A 100% client-side gallery — view your own Data folder in the browser, nothing uploaded | [`gallery/`](gallery/) |

Plus documentation in [`docs/`](docs/): the reverse-engineered
[file-format reference](docs/VIPER_RACING_FILE_FORMATS.md), and a
[history of the modding community](docs/MODDING_HISTORY.md) — the people, the
tools they built, and how the formats came to be understood.

**Try the Library in your browser:** https://herbfargus.github.io/viper-racing-modding/ — open your own Viper Racing **Data** folder and browse every car and track in 3D, entirely client-side (nothing is uploaded).

**Browse the docs online:** the [file-format reference](https://herbfargus.github.io/viper-racing-modding/docs/reference.html) and the [modding history](https://herbfargus.github.io/viper-racing-modding/docs/MODDING_HISTORY.html) (both also in [`docs/`](docs/) as Markdown).

> **Repo naming:** the GitHub repo is `viper-racing-modding`; the Python package is
> `vrmod`; the desktop app's product name is "Viper Racing Mod Manager". The
> **community gallery** (a separate, future repo — assets hosted alongside a
> view-only browser gallery) is deliberately *not* here; this repo is tools only.

## Layout

```
vrmod/            the toolkit: parsers/builders, CLI, and the web UI (switcher_ui.py)
  assets/         three.min.js (bundled for offline 3D) + stock slot icons
desktop/          the standalone app: app.py, the PyInstaller spec, icon
gallery/          the client-side Library (Pyodide + a worker pool), provider-seam
docs/             reverse-engineered file-format reference
scripts/          build helpers (build_gallery.py builds gallery/vrmod.zip)
```

Game data is **never** committed — the toolkit reads your own install, and
`.gitignore` blocks `*.car/.trk/.tra/.res`, `race.bin`, etc.

## The toolkit / CLI

`vrmod` is pure standard library apart from `capstone` (used only by the optional
`race.bin` vertex-buffer patch — imported lazily, so everything else, including the
whole viewing path, runs with no third-party dependency; that's what lets it run
under Pyodide in the browser gallery).

```bash
python -m vrmod.cli switcher "C:\path\to\Viper Racing\Data"
```

## The desktop app

```bash
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python desktop\app.py
```

It opens on a landing screen; choose your Viper Racing **Data** folder (the one with
`race.bin` and your `.car` files) and it remembers it next time.

### Building the standalone .exe

With the venv set up, plus PyInstaller (`pip install pyinstaller`):

```bash
.venv\Scripts\python -m PyInstaller --noconfirm desktop\viper-mod-manager.spec
```

Produces a **single file**, `desktop\dist\ViperModManager.exe` (~17 MB) — that one
file *is* the whole app. The spec bundles `vrmod/assets/` (three.js + slot icons),
capstone's native lib, pywebview's backend, and the app icon (`desktop/icon.ico`,
generated by `desktop/make_icon.py`). Paths in the spec are anchored to its own
location, so it builds from anywhere.

## The client-side Library (gallery)

A view-only browser gallery: drag in your **Data** folder and browse every car and
track in 3D, entirely client-side (Pyodide runs `vrmod` in WebAssembly — files never
leave the browser). Grid thumbnails render in a **pool of Web Workers** (parallel
across CPU cores) and load lazily as you scroll; the interactive 3D viewer builds on
click. Its data source is an **asset provider** ([`gallery/providers.js`](gallery/providers.js)) —
today `LocalFolderProvider`; the seam is where a future community gallery drops in.

```bash
python scripts\build_gallery.py          # builds gallery/vrmod.zip from vrmod/
python -m http.server -d gallery 8000    # then open http://127.0.0.1:8000/
```

(`gallery/vrmod.zip` is a build artifact — gitignored, regenerated from `vrmod/`,
so the gallery can never drift from the toolkit.)
